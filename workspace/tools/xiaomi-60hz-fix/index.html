Xiaomi / MIUI stuck at 60Hz on a 120Hz screen — the hidden setting nobody tells you about

You set 120Hz in Settings. Ten seconds later it is back to 60Hz. It is not your screen, not a bug, and not something you did. There is a second, hidden refresh-rate setting that MIUI silently rewrites in the background — and here is how to stop it for good, with no root.

Tested on a Redmi (2409FPCC4G), Android 16 / HyperOS, MediaTek. Works via ADB from a PC or directly on the phone.

1. The symptom

Everything looks like it should work. You go to Settings → Display → Refresh rate, pick 120Hz, and the phone feels smooth — for a moment. Then it drops back to 60Hz. You check the setting again, it still says 120. You reboot. It happens again. Every guide online says “just enable 120Hz in Settings”, which is exactly what you already did.

2. The real cause (with proof)

On stock Android, the refresh rate is controlled by a single setting, peak_refresh_rate. On MIUI and HyperOS there is a second setting that takes priority:

miui_refresh_rate

When the two disagree, MIUI follows miui_refresh_rate and ignores the standard one. So you set 120 everywhere you can see, while the hidden value — and something in the background — keeps it at 60.

That “something” is com.miui.powerkeeper, Xiaomi’s battery-optimisation service. Its job is to switch between 60Hz and 120Hz automatically to save battery, and it rewrites the setting on its own schedule. You can prove it by watching the settings history:

adb shell dumpsys settings | findstr miui_refresh_rate

On the tested device it looked like this — the same package flipping the value back and forth every few seconds:

16:08:27  value:120  packageName:com.miui.powerkeeper
16:08:37  value:60   packageName:com.miui.powerkeeper   <-- reverts
16:08:43  value:120  packageName:com.miui.powerkeeper
16:08:44  value:60   packageName:com.miui.powerkeeper   <-- reverts again

Why this is hard to find: the visible setting says 120 the whole time. The value that actually matters lives in secure settings, is exposed in no menu, and is reverted within seconds. That is why “just set 120Hz” advice fails, and why this problem appears to have no documented fix.

3. Diagnose your device in 30 seconds

These commands need ADB (see section 6). Run them one by one.

What mode is active right now

adb shell dumpsys SurfaceFlinger | findstr peak-refresh

Look for 60.00 Hz (stuck) or 120.00 Hz (fine).

What your screen actually supports

adb shell dumpsys display | findstr supportedRefreshRates
adb shell dumpsys display | findstr mActiveModeId

A 120Hz panel lists something like [60.0, 120.0, 90.0]. If 120.0 is absent, the hardware does not support it — stop here.

Read both refresh settings

adb shell settings get system peak_refresh_rate
adb shell settings get secure miui_refresh_rate
adb shell settings get system miui_refresh_rate

If the miui_refresh_rate values are 60 or null while peak_refresh_rate is 120, you have found the mismatch.

Catch the culprit

adb shell dumpsys settings | findstr miui_refresh_rate

If you see packageName:com.miui.powerkeeper writing value:60, that is your saboteur. Continue to the permanent fix.

4. Quick fix (try this first)

Force the hidden setting to 120 in every namespace and see whether it holds:

adb shell settings put system peak_refresh_rate 120
adb shell settings put system min_refresh_rate 120
adb shell settings put secure miui_refresh_rate 120
adb shell settings put system miui_refresh_rate 120

Wait one minute, then check again with dumpsys SurfaceFlinger | findstr peak-refresh.

If it stays at 120Hz — great, you are done. Some devices only needed the hidden setting corrected.

If it reverts to 60Hz — PowerKeeper is reverting it. Do not repeat these commands; go to the permanent fix.

5. Permanent fix (the one that works)

The usual tricks do not work on modern MIUI, and it is worth knowing why:

  • am force-stop com.miui.powerkeeper — the service is restarted by the system within seconds.
  • pm disable-user com.miui.powerkeeper — fails with SecurityException: Cannot disable system packages on Android 14/15/16.
  • appops set ... WRITE_SETTINGS deny — not respected; the service is restarted.

The method that sticks is to uninstall the package for the current user. This does not touch the system partition, needs no root, and is reversible at any time.

Uninstall PowerKeeper for user 0

adb shell pm uninstall --user 0 com.miui.powerkeeper

You want the single word: Success.

Confirm it is gone

adb shell pm path com.miui.powerkeeper
adb shell ps -A | findstr powerkeeper

Both should return nothing. If pm path still prints a path, it was not removed.

Set 120Hz again

adb shell settings put system peak_refresh_rate 120
adb shell settings put system min_refresh_rate 120
adb shell settings put secure miui_refresh_rate 120
adb shell settings put system miui_refresh_rate 120

Wait and re-check

adb shell dumpsys SurfaceFlinger | findstr peak-refresh

Give it a full minute. It should read 120.00 Hz and stay there.

Survive a reboot

adb reboot

After it boots, connect again and re-run the check. If it is still 120Hz, the fix is permanent.

Result on the tested device: after removing PowerKeeper and setting the hidden value to 120, the display held 120Hz indefinitely and stayed there through a full reboot.

6. Setting up ADB (one time)

  1. On the phone: Settings → About phone, tap MIUI/HyperOS version seven times to unlock Developer options.
  2. In Developer options, enable USB debugging.
  3. On the PC, download Platform Tools from Google’s Android developer site and open a terminal in that folder.
  4. Connect the phone with a data cable (not charge-only) and run adb devices.
  5. Approve the dialog on the phone, ticking Always allow from this computer.

Windows note: replace findstr with its macOS/Linux equivalent, grep. Everything else is identical on all platforms.

7. Fix without a PC

You do not need a computer. Any on-device shell able to talk to the local ADB daemon works the same way — for example Termux with a wireless ADB connection, or a root shell. The three commands that matter are unchanged:

pm uninstall --user 0 com.miui.powerkeeper
settings put secure miui_refresh_rate 120
settings put system miui_refresh_rate 120

This is the part almost never mentioned in existing guides, and it matters for anyone without a PC nearby.

8. How to verify it worked

adb shell dumpsys SurfaceFlinger | findstr peak-refresh
adb shell settings get secure miui_refresh_rate
  • peak-refresh-rate : 120.00 Hz — and it does not drop.
  • miui_refresh_rate returns 120 and stays there.

If both hold after a reboot, you are done. If not, re-check that pm path com.miui.powerkeeper returns nothing.

9. How to revert (back to adaptive)

Nothing here is permanent at the system level. To restore Xiaomi’s adaptive behaviour:

adb shell pm install-existing com.miui.powerkeeper
adb shell settings put secure miui_refresh_rate 60

Remember that 120Hz constant uses more battery than adaptive switching. If battery life matters more on a given day, this is your way back.

10. Warnings

Never remove core system packages. This guide targets exactly one battery service. Do not uninstall things like com.android.phone, com.android.systemui, com.android.vending (Play Store), com.google.android.gms, or any com.android.providers.* package — doing so can leave the phone unable to boot, recoverable only by reflashing firmware.

pm uninstall --user 0 is reversible with pm install-existing <package>, but only if you remember the package name. Note down anything you remove.

11. Compatibility & disclaimer

Verified on a Redmi (model 2409FPCC4G), Android 16 / HyperOS, MediaTek display. The mechanism — a hidden miui_refresh_rate setting reverted by com.miui.powerkeeper — is present across recent MIUI and HyperOS builds, but exact package names and setting names can differ between regions and versions.

Always run the diagnostic steps first, so you react to what is actually happening on your device rather than assuming.

If this saved you an evening of frustration, pass it on — this problem is far more common than the lack of documentation suggests.

Guide written from a real, reproducible device diagnosis. Commands are non-destructive by design and reversible.
